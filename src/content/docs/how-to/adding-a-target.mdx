## Prerequisites

- You must own the domain or hold explicit written authorisation to test it. Scope is enforced in code, not in the prompt: an unauthorised target is capped at passive observation and active testing is refused outright.
- The application must be reachable from wherever the deployment runs.
- **If the hostname CNAMEs out of your own infrastructure, an administrator must authorise the delegation target by name before the run will start.** Controlling a DNS zone is not the same as controlling the machine behind it, so a chain that leaves your declared scope refuses the run rather than warning about it. Anything behind a CDN hits this. See below.
- **For authenticated coverage, the app must offer self-serve email/password signup.** Most of an application's attack surface (IDOR, broken access control, privilege escalation) lives behind login, and the agent acquires its own test identities by registering real accounts. See below.

## Authenticated testing requires self-serve signup

To test everything behind login, BattleTest signs up its own disposable accounts (using throwaway mailboxes it controls), logs in, and drives the app as a real user — including creating a second identity to probe for cross-user access flaws (IDOR/BOLA/RBAC). The second identity is also how findings are confirmed: nothing is reported unless it was replayed against the running system and reproduced from a second, unrelated account.

For this to work, the target must allow **self-serve registration with email and password** (or another credential BattleTest can create on demand).

<Warning>
  **SSO-only apps get discovery-only coverage.** If the only way in is "Sign in with Google/GitHub" and there is no email/password signup, BattleTest will **not** automate a third-party login (it's outside your authorisation and against those providers' terms). It reports the app as SSO-only and tests only the unauthenticated surface. To get authenticated testing, expose a self-serve email/password signup — even a staging-only or feature-flagged one is enough.
</Warning>

<Note>
  Seeing shallow results on a login-gated app? Check that a fresh visitor can register without SSO. A hard SSO wall, an invite-only signup, or an email-domain allowlist all block automated account creation and cap coverage at the public surface.
</Note>

## Hosts served by someone else's infrastructure

Both authorisation paths — declared scope, and the DNS TXT proof — establish something about
a **name**. Neither establishes anything about the machine that answers for it. A hostname can
legitimately pass both while resolving, by CNAME, into a multi-tenant host you do not own; an
exploit lands on the machine, not on the name, and the tenants sharing it authorised nothing.

So when the CNAME chain leaves the scope this deployment declared, the run is **refused** until
an administrator authorises the delegation target itself. `www.example.com` →
`d111.cloudfront.net` is the same DNS shape as the dangerous case and is entirely ordinary —
nothing in DNS distinguishes "my CDN" from "someone else's tenant", because that is a fact
about a commercial relationship. A person has to state it.

Authorise it in **Settings → Testing scope**, on the same record that gates a public host: the
hostname, a justification (required — it is the whole reason the record exists rather than a
boolean), an approver, and an expiry that defaults to 90 days. It is revocable and it is
visible to an auditor afterwards. Approve `d111.cloudfront.net` once and every hostname behind
that distribution stops being friction.

Two details worth knowing before you hit this:

- **Matching is exact.** Approving `vendor-saas.com` does not authorise `you.vendor-saas.com`,
  because a suffix match would authorise precisely the set of names belonging to other people.
- **A lookup that does not complete also refuses.** A CNAME loop, a chain longer than eight
  hops, and a resolver that stops answering are each reported as their own failure rather than
  treated as a chain that ended. "We could not tell who serves this" is not a weaker version
  of "nobody else does".

An **address** outside your declared CIDR ranges is reported but does **not** block. There is no
named party to authorise for an anycast edge address, and a check that fires on ordinary public
hosting is one operators route around rather than use. Address checking only happens at all if
you declared CIDR scope — without that there is no baseline for which addresses are yours.

## Environments and domains

A target is described as an **environment**: one application, and every hostname that belongs
to it. `api.example.com` and `app.example.com` are one environment, not two. One battletest
run covers the whole environment regardless of how many hostnames it contains.

Group by application, not by DNS. Splitting one application across two environments hides
exactly the flaws worth finding — an agent that can move from the web app to the API in a
single run is what surfaces a cross-service access-control break.

## Permission tiers

Each environment carries a permission tier that decides what the agent is allowed to do to
it. The tier is a code-level control: offensive tooling is withheld at lower tiers rather
than the agent being instructed not to use it. Raising a tier is an explicit, recorded
approval, and steps that could change state pause for a human decision.

A first assessment normally starts read-only, and the tier is raised once the discovered
inventory has been reviewed. See [How Live BattleTest works](/docs/concepts/live-battletest-overview#the-permission-tier-model)
for what each tier permits.

## What a run reports

A run reports what it confirmed and what it could **not** reach. The second half matters as
much as the first: coverage you did not get is a fact about the assessment, not something to
be quietly omitted from it. Discovery output — the endpoint inventory the run built — is
part of the record.

For the shape of the report itself, see [Scan results](/docs/reference/scan-results).
